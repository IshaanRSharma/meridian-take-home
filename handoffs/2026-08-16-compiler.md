## 2. The product in six lines

A non-technical process owner draws their SOP on a whiteboard. An AI reviewer
reads the drawing, notices what it does not say, and asks questions. The owner
answers in plain English. Answers become statements attached to cards. When
nothing blocking remains, the board **freezes** into a spec, and a coding agent
turns that spec into a running Temporal workflow.

The thing being graded is whether **the frozen spec is actually sufficient to
hand to a coding agent**. Everything else serves that.

```
                  seeds/prealert_board.json

```

**Four cards, and only four.** Event · Action · Check are *steps* and connect
with edges. **Entity is a thing** — referenced by name inside cards, never
edge-connected, no layout position. This was settled after some back and forth;
do not add a fifth card type without a very good reason.

**It is a state machine, not a DAG.** `repeat` edges make it cyclic. This is
load-bearing for the Section 0 essay and there is a test that demonstrates it:
`test_answering_the_termination_question_makes_the_graph_cyclic`.

**The completeness contract is `findings()`, not Pydantic validators.** A
half-filled card must stay saveable — the owner is mid-thought. Conditional
requirements live in `findings()` and *nowhere else*. Its `reason` string is the
text rendered on the card, so a new field cannot be added without writing the
sentence a warehouse supervisor will read.

**Lint and decisions are different things** (`docs/design/compiler.md` has the
table). Lint says *something is missing* and is provable. A decision says *the
drawing chose something* and may be wrong. Six sweeps — sequence, termination,
convergence, boundedness, entry, coverage — systematic over structural
properties. The user was explicit: **no hardcoding for shapes or patterns.**

**Two loops, not one.** Comment loop: `open → answered | rejected` — settles
business knowledge. Revision loop: `answered → resolved | open` — makes the
drawing show it. The transition table is `review.py:_ALLOWED_TRANSITIONS`.

## 8. How to work here (the user was explicit about all of this)

**The rhythm, every file, in order — do not skip or reorder:**

1. **Plan.** State the contract and *predict* what it produces against the seed
   board before writing anything.
2. **Tests.** Test the product's logic, not the code's surface. The good ones
   assert an absence, hold something to a floor, or encode a product property.
3. **Implement.**
4. **Review.** `make check`, then **mutation-test**: break each new condition on
   purpose and confirm a *named* test fails.

This is not ceremony. The planning step has caught real design errors that would
have been expensive later — the two-loop model, the `Fill.per` grain, the
entity-vs-edge relationship.

Also: **not freely autonomous** — the user wants control over code output, so
propose before writing. Stripe/Google code quality. **No AI-slop comments**; a
comment earns its place by saying *why*. No weird shortcuts to get output.

**Commit messages are prose about the decision**, not a changelog. Look at
`git log` for the register.

## 9. Non-obvious things that will bite

- **`meridian/.env` and `ui/.env`** — env files live *inside* each half, because
  `env_file` is CWD-relative. An earlier fix walked `parents[4]` and the user
  called it a janky config workaround. Both are gitignored.
- **Repository tests run inside a transaction that is always rolled back**
  (`tests/repositories/conftest.py`, not `tests/conftest.py`). An autouse
  `_release_pool` fixture closes the pool after each test — the pool is a
  module-level global bound to the loop that created it, and pytest-asyncio
  gives each test a fresh loop, so without it the *second* test fails with
  "Event loop is closed".
- **Which database those tests hit is currently inconsistent — verify before
  trusting it.** `Claude.md`'s decisions log says local Postgres for tests and
  Supabase for real; `tests/conftest.py` says the same; but
  `tests/repositories/conftest.py` claims Supabase and `DATABASE_URL` in
  `meridian/.env` points there, so `make test` reaches the live project.
  Related: `make db` starts postgres **17** while Supabase is **15**, which
  defeats the stated reason for testing locally. Both unresolved as of this
  handoff.
- **Pydantic's Rust regex rejects lookahead**, so `DomainModel` sets
  `regex_engine="python-re"`. The ISO-8601 duration pattern needs it.
- **`BOARD_KEY` is `{1,63}`, not `{2,63}`** — edge keys are `e1`.
- **`findings()` merges on `(anchor, field)` at the worst severity**, so a board
  rule can *raise* a card's severity but never *suppress* it. A card-level
  finding that a board rule needs to cancel must be deleted, not overridden.
  This bit us once with `identified_by` on produced entities.
- **asyncpg ships no `py.typed`** — there is a mypy override for it.
- **`git checkout --` during mutation testing reverted a real change once.**
  Mutate in the editor and undo deliberately, or stash.

## 10. Known gaps and open questions

- **Seven decisions, cap of six.** Nothing ranks them by value. The signals —
  corpus evidence, prior rejection rates — arrive with the reviewer.
- **A check whose result changes nothing is not surfaced.** Legal, and exactly
  what `CAAU4056270` does. Worth questioning, but no sweep asks it; inventing one
  now would be speculation.
- **Two rules could produce the same `(anchor, field)` at the same severity.**
  The merge keeps whichever ran first. `RULES` is a fixed tuple so it is
  deterministic, but order-dependent.
- **`status` in the eval output has no check behind it.** Only the process owner
  can say what closes a shipment. It lands as an `important` finding.
- **`invoices_mismatched_asn`** has no source on the seed board either — also an
  intended round-2 finding.
- **AI proposing a canvas patch is cut**, and lives in the README's future
  enhancements. So does dropping a sample PDF to derive fields.

## 11. Where the eval set fits

`fixtures/expected/shipments.json` — five shipments, nine columns each. Seven of
the nine come from **two checks** via `Fill(measure, field, per)`, where `per`
is the grain. `CAAU4056270` reports `invoices_failed: 1` *and* `goods_failed: 2`
from one rule counted at two grains — that is the whole reason `per` exists.

`coas_valid` is scoped `per_line_item`, not `per_shipment`: `coa_total: 5`
counts batches. This was a real modelling error found by a field that did not
exist yet.
